# WATER-PERIOD-V2 — correctness-first acceptance and deployment

## Engineering priority

Correct business and accounting invariants take precedence over compatibility with old data or old client behavior. Do not retain incorrect algorithms or weaken acceptance tests to accommodate old records. Existing records and a live database are not prerequisites for code acceptance; their remediation or reset is a separate, explicitly controlled deployment operation.

## Contract

- New readings use the actual observation date, not visit schedules. The first interval begins at installation or, if absent, the documented service start. Subsequent intervals use the prior observation date and value.
- The existing historical tariff service prices the stored interval. Never fabricate a tariff, split an unmeasured period or silently rewrite an issued invoice.
- There is one writable interval algorithm: actual observations. Calendar-era records cannot be edited through the normal reading workflow; their existing marker is retained solely to distinguish old records from validated observations. Client-submitted period hints are retained separately for replay identity only, never for computation.
- Protect baseline dates and values, earlier reading anchors, and billed evidence against edits/deletion. Local pending readings with successors must not be silently changed.

## Quantity precision

Meter values, installation baseline and derived consumption use DECIMAL(12,2). The model subtracts integer hundredths, rejects decreasing values, and never accepts client-supplied usage as authoritative. Posting does not recalculate stored quantities. API input permits at most two decimal places; Flutter offline subtraction, administrative reports and spreadsheet exports preserve the fractional units. Historical tariff line rounding remains per line. Tests cover 35.50 units at 600.00, a 0.01-unit difference, zero usage, edits and invalid precision. The baseline is captured during meter creation/replacement and the replacement has its own installation date, regardless of financial history. API and mobile cache select the latest reading by observed date rather than insertion order or calendar forecast. No historical quantity or financial backfill is part of these schema migrations.

## Write-path and database safeguards

Normal database setup never imports historical subscriber/reading rows. The old archive seeder is retired; optional demo initialization uses `SyntheticObservationSeeder` in local/testing environments only, without truncation. The former screenshot seeders delegate to that same path. Existing backups remain independent of application initialization.

MySQL 8.0.16+ uses an enforced row CHECK for observed intervals and exact quantities, without SUPER or trigger privileges. SQLite uses insert/update triggers. The historical marker is excluded from that row constraint, so privileged raw MySQL writes can still assign it; normal model creation rejects that marker and updates cannot change it. Do not grant unrestricted SQL write access to clients. Row constraints do not prove cross-row continuity; subscriber/meter locks, current-reading locking queries and the model enforce that contract. Deleted observations cannot be restored into the chain through the model. MySQL CI additionally exercises independent-process races for same-date reading insertion and concurrent invoice issuance.

## Code acceptance and separate production deployment gate

1. Require all acceptance jobs on the exact head SHA (Laravel full, MySQL and Flutter full). Do not waive failed tests.
2. For production deployment only: take and verify a backup of the current database. Restore into an isolated MySQL database, never the live schema.
3. Record before/after counts and financial totals for readings, invoices, payments, transactions and invoice_tariff_lines (if present); apply pending migrations to the isolated copy only.
4. Run `php artisan water:audit-observation-intervals` and `php artisan water:audit-historical-tariffs`. New invalid chains and pricing blockers require resolution. Legacy early readings are explicitly reported for review; no automatic correction.
5. Add a synthetic reading on the isolated copy, verify its actual interval, historical price, invoice and ledger balance; verify original financial records are unchanged.
6. Exercise Android/Windows offline delayed sync, latest reading edit, duplicate retry and rejection of a stale/retired meter. Record evidence before production rollout.

A successful fresh-schema CI run is not a substitute for the actual-data migration rehearsal or field-device acceptance.

## Physical cash settlement

New and currently open sessions use opening cash plus active cash receipts, excluding bank transfers and checks. All payment methods still contribute to subscriber balances; treasury refunds are separate from collector cash. Closed historical snapshots are not recalculated and carry `legacy_recorded` in the API if their settlement basis was not recorded. A new closure uses `physical_cash` and preserves the original snapshot even after a documented correction. API exposes cash, non-cash and total receipt collections separately. A new offline payment arriving after close still requires explicit session-identity and exception workflow; do not interpret the concurrent close test as complete offline reconciliation.

## Deferred payment session identity

Flutter freezes the known cash-session ID and payment date before the first send, then retains both in its persistent queue. New deferred payments require a known original open session owned by the authenticated collector and a stable UUID/date. Exact existing receipts may be replayed after closure. Unposted late or legacy unidentified operations receive HTTP 409 for human reconciliation; no automatic transfer to a newer till or mutation of closed totals. An independently reviewed late-receipt posting workflow and cross-device close reconciliation remain required before field acceptance.

## Late receipt review (separate handover only)

Authenticated collector submits an immutable late receipt claim for their own closed till. Global issuance lock reserves its UUID; duplicate claims replay, differing claims conflict. An independent supervisor must verify an approved original till and documented separate treasury cash handover or non-cash receipt confirmation, with unique evidence reference. Approval posts one normal subscriber receipt through PaymentService without assigning it to any collector till; the review links original till, payment and approval evidence. Reject requires evidence; no financial posting. Already-included cash, disputed receipt identity, unidentified legacy till and missing treasury evidence must remain unresolved until independently reconciled; this is not a treasury ledger or automatic reconciliation. Closed snapshots remain intact. API is separate from standard posting. On deferred payment HTTP 409, the Flutter queue submits a claim when it knows the original till; the server revalidates all conditions. The local operation remains in needsAttention until a successful retry returns its actual posted receipt. The Filament cash-session table provides an independent supervisor decision action. Real-device and end-to-end acceptance are still required.

## Already-counted cash allocation

For approved physical-cash settlements only, the positive original counted-minus-expected variance (validated against the frozen snapshot) is a conservative maximum. Each approved already_counted claim consumes its exact amount under the same global issuance and cash-session locks. The original cash variance is never rewritten; API/PDF disclose allocated and unallocated surplus separately. Legacy snapshots, negative/zero variance, and amounts exceeding available surplus cannot be allocated. Later bookkeeping corrections do not increase this capacity. No additional cash movement is created by posting a reviewed receipt; the subscriber subledger is credited once. Ordinary voiding of approved exceptional receipts is prohibited; independently evidenced refunds or account transfers are separate operations. This is not a complete treasury general ledger; cash already counted but offset by a shortage requires separate investigation, not automatic allocation.

## Original ledger posting integrity

The service validates persisted document type, owner, meter provenance, exact signed amount and valid original state before writing. Multiple or deleted original postings are rejected, never guessed. Reversals check the original reference including retired meter identity. `ledger:migrate` is now a read-only original-invoice/payment audit, not a rebuild; the old temporary destructive script is disabled. This limited audit does not yet certify all refunds, transfers, reversals or general ledger constraints; further reconciliation and database enforcement remain required.

## Read-only document reconciliation

`php artisan ledger:audit [--subscriber=ID] [--json]` inspects non-deleted subscriber accounts independently under their account lock. It checks original and required reversal postings, refund and transfer identities, unexpected postings, net ledger versus independently calculated document balances, and latest allocation revision hash, per-invoice and per-source totals. The existing allocation reconciliation endpoint exposes `document_reconciliation` and cannot report a match for offsetting posting errors. No repair/replay is performed. Unsupported legacy postings are reported, not silently accepted. This is a diagnostic account-subledger audit, not a complete treasury audit; cross-account checks are not a single global snapshot, and database-level posting uniqueness/immutability is a further step.\n
## Database ledger protection

A unique index on (reference_type, reference_id, type) prevents duplicate referenced postings even through raw SQL. Pre-existing duplicate keys stop migration without deleting or merging financial history. Unreferenced legacy rows remain auditable; they are not asserted valid. MySQL/MariaDB replace the ledger subscriber cascade and meter SET NULL foreign keys with RESTRICT; SQLite uses parent-delete triggers to avoid rebuilding a table referenced by financial corrections. SQLite installs append-only triggers automatically. MySQL/MariaDB require an explicit privileged `php artisan ledger:protect --install` followed by `php artisan ledger:protect --check` as a production acceptance gate (shared hosting may deny CREATE TRIGGER). The check returns failure when a trigger or unique index is absent; successful check verifies named guards are present, not that a privileged administrator cannot remove them. No new arbitrary SQL inserts are certified valid by this migration; the service and ledger audit still validate document identity. Meter retirement alone may move a current meter ID to matching retired provenance with all monetary fields unchanged. Historical correction no longer redundantly updates the new ledger entry. Retired ad hoc maintenance scripts now exit without bootstrapping or modifying data. Corruption tests deliberately disable/reinstall the SQLite update trigger solely in their isolated test fixtures. DDL and backup/restore permissions must be restricted; triggers cannot protect against privileged DDL, TRUNCATE, or restoring altered backups. No production data was modified.

SQLite's INSERT OR REPLACE can bypass a delete trigger with recursive triggers disabled; a separate BEFORE INSERT guard blocks replacement by primary key or by referenced posting key. The MySQL CI job explicitly enables trigger creation in its disposable MySQL container only, then runs a dedicated non-transactional migration/install/guard test. No hosting configuration is changed. For an existing SQLite development database whose ledger migration already ran, run `php artisan ledger:protect --install` and verify `--check` to install the additional guard.

## Shared financial reporting basis

Filament and dashboard/report API now use one valid-receipt query with half-open date bounds, six calendar months anchored on the first day, and no future days in the current dashboard month. Fake sparkline samples are removed from Filament and Flutter parsing. Current per-subscriber ledger debt and credit are summed separately without netting different subscribers, and exposed independently of the selected invoice cohort (current outstanding of invoices issued during the period). Flutter displays both when supported and preserves them in cached reports; missing older-server fields remain unavailable. Net valid receipts less disbursed refunds is not a treasury cash balance or accrual revenue. The API explicitly identifies receipt, refund and ledger date bases. Historical as-of balance, treasury reconciliation, report/export parity and cross-query snapshot consistency require further work. No historical records have been changed.

## Historical subscriber statement

The independent `GET /api/subscribers/{id}/ledger-statement?from_date=YYYY-MM-DD&to_date=YYYY-MM-DD` uses posting dates (`transactions.created_at`), chronological ID tie-breaking, integer minor-unit running balances, and the subscriber lock. Opening includes all recorded active postings before the first day, closing includes all before the next day after the end date. Reversals are separate entries; original receipts are not removed based on their current void status. Undated active legacy rows block issuance rather than inventing a posting date. `/xlsx` and `/pdf` use exactly the same projection; XLSX also requires export permission. The old statement and Flutter local PDF are not yet replaced; UI wiring and a real browser PDF acceptance run remain pending. This proves conservation of recorded entries, not independent document correctness; use ledger:audit for reconciliation. Reports do not rewrite historical data.

## Official statement user interfaces

Filament subscriber list/edit actions open a dedicated resource page with date filters, server-authoritative opening/debit/credit/closing totals and chronological rows. Web downloads enforce subscriber view policy, with explicit export permission for XLSX. Flutter's existing filtered activity tab links to a dedicated online-only official statement screen, which validates the response contract and downloads the original server PDF/XLSX, not the old locally calculated statement. Filtered meter activity is labelled as such; it is not a separate account. Exports re-query the period at request time, so new postings since display may change results. UI and full framework acceptance are still required.

Official UI downloads now send a SHA-256 statement identity returned by the server. If the current projection differs (including posting, account, or meter provenance changes), the download returns HTTP 409 and requires a refreshed statement instead of silently exporting different numbers. Older direct API callers can still request a new projection without a hash. The hash is a version check, not a signature or independent audit certificate.

## Verified cash custody handovers

Approval is a review of the collector's count, not evidence of treasury receipt. The new append-only application document `cash_handovers` records physically received cash in separate tranches with normalized unique receipt references, receiver identity, actual receipt date and evidence. Only a permitted independent receiver may record cash against an approved, internally consistent physical-cash snapshot. Total handovers cannot exceed the original counted cash (including opening float and any surplus already physically counted); separate late receipt handovers are outside this ceiling. No subscriber payment, revenue, refund or ledger entry is created by this custody transfer. Legacy snapshots are not eligible; no historic cash receipts are fabricated. API, Filament and daily PDF expose the unverified remainder separately. This records evidence of receipt, not a verified treasury opening/closing balance, nor a general ledger. Bank/cheque settlement, opening-float funding and onward deposits/disbursements need separate documents. No raw SQL immutability triggers for the new handover table are claimed. Existing role capability for independent late-receipt review is reused pending a distinct treasury permission catalog.

The daily JSON and PDF reports list individual custody receipts (reference, actual receipt date, receiver ID and amount). The report reads the session, receipts and handover summary within the session lock so concurrent authorized custody recording cannot cause disagreement between the individual amounts and displayed total. Evidence descriptions remain in the underlying custody records and audit log.

## Treasury foundation — restricted, evidence-based posting register

No treasury account or opening balance is seeded. An authorized super_admin explicitly establishes each named cash or bank account with a verified opening balance as of the start of a chosen day and a unique evidence reference. The initial posting register accepts only already documented cash handovers and cash/bank refunds, with the correct channel, a globally unique source and a date on or after the account opening date. A source cannot be silently reassigned to another treasury account. Amount and date come from the persisted evidence, not from client input. The register does not create subscriber receipts or alter their ledger. Posting is explicit, not automatic; unposted evidence counts are channel-wide and not assigned to a specific account. Older evidence may already be included in the verified opening and must not be reposted. A negative recorded subtotal is an exception, not a reason to hide an actual disbursement. The subtotal is deliberately named provisional_recorded_balance_minor and certified_balance is false: opening float funding, bank collections/deposits, separately handed-over late receipts, operating disbursements, internal transfers and actual cash/bank reconciliation are not yet integrated. No production opening is established by this change. Database raw-SQL immutability and treasury-specific delegated permissions/UI are further acceptance tasks.

## Collector opening funding

A new positive opening must be created by an independent super_admin through `POST /api/treasury/accounts/{id}/fund-collector` after actual documented cash delivery. The cash-only account, funding evidence, new collector session and negative treasury posting are recorded in one transaction using the global issuance lock. Ordinary collector opening is zero only; Flutter offers a zero opening and instructs the collector to refresh after authorized funding. A repeated identical reference returns the original session (even if later closed); conflicts cannot fund twice. Historical positive openings without a funding source are reported as `legacy_unverified`; no backfill is invented. The register remains provisional: actual disbursements are recorded even when the partial subtotal becomes negative, and are flagged by reconciliation. This is evidence of cash already delivered, not authorization to spend or a certified available balance. Full custody return still uses the counted-cash handover and explicit treasury posting. A permanent float carried across sessions, funding approval workflow, dedicated treasury roles, Filament funding interface, database-level raw SQL safeguards and complete cash reconciliation remain pending.

## Internal treasury transfers

An evidenced dispatch debits the source cash/bank account immediately and records cash in transit. Only an independent authorized receiver with separate evidence of full receipt credits the destination. No destination balance is increased on dispatch. Both legs use immutable application documents, unique source foreign keys and distinct evidence references, with global issuance and ordered account locks. Replaying the same evidence returns the original transfer/receipt; conflicts fail. Dispatch and receipt are separate atomic transactions. `GET /api/treasury/transfers` exposes outstanding transit and reconciliation exceptions; per-account inspection checks both legs, including missing or mismatched rows. No subscriber ledger or payment is touched. Full receipt only: discrepancies, partial receipt, charges, loss or cancellation require separately designed correction documents; until then the original amount remains in transit, not silently written off. This register documents movements already executed, not payment authorization or proof of available funds. All accounts are assumed to use the same project currency; currency conversion is unsupported. No automatic legacy import, bank integration, dedicated UI, or raw-SQL immutability claimed. Balances remain provisional.

## Bank statement reconciliation — evidence only

Bank statements are manually entered from actual bank evidence (no live bank connection). Each statement belongs to one bank account, has non-overlapping inclusive dates from the account opening onward, signed opening and closing amounts, and up to 1000 uniquely identified nonzero signed bank lines. Stable bank transaction references are unique per account. Adjacent statement boundaries must agree when both exist. Opening plus signed lines must equal closing exactly in minor units. Import and its audit event are atomic. A separate super_admin explicitly matches one bank line to one existing same-account, same-period treasury posting with identical signed amount and evidence; importer and matcher must differ. Same match retry is idempotent; competing match conflicts are rejected. Matching writes no financial posting. The report exposes bank/recorded opening and closing, signed unmatched sums and individual unmatched items, invalid matches, the opening difference, and the signed conservation identity. Timing differences across periods, one-to-many matches, correction/unmatching documents, automated file parsing, bank feed authentication, bank fees and direct bank collection posting are not covered. Matching does not prove bank evidence authenticity; even a fully matched period remains uncertified because treasury coverage is incomplete. No historical entries are altered. Raw SQL guards and Filament workflow remain pending. No opening or statement is seeded.

The report also recomputes the original canonical statement content hash from persisted header and individual lines, detects offsetting changes, and rejects new matches or import replays against a changed statement. This is an integrity check, not a cryptographic signature or protection against privileged modification of both data and hash.

## Physical treasury cash count (not period closure)

A super_admin records a current physical count on a cash account, with a unique reference, evidence and observed system time. The operation locks the financial register, saves the provisional recorded subtotal and hashes the actual account and posting records at the time of entry; it creates no treasury or subscriber posting. A separate super_admin reviews the documented count (accept or reject) with evidence only while the ledger snapshot is unchanged. The original count and decision remain separate records. Any later account/posting change makes the snapshot stale, including later legitimate movements: this is deliberately conservative, not a historical as-of reconstruction. The original variance remains unchanged. Equal recorded/count totals are not certification; sources remain incomplete and raw SQL protections are pending. Cash count evidence does not establish a complete period close, authorize write-offs, or verify that a person actually counted cash. No automatic variance adjustment, fee posting, or financial period lock is enabled. These require distinct evidence-based correction workflows and complete coverage/acceptance. No existing records changed.

## Documented bank charges (G1A #56)

An independent super_admin (not the statement importer) may classify a genuine standalone bank debit as a fee through `POST /api/treasury/bank-statements/{id}/fees`, with unique reference, reason and independent evidence. Account, negative amount and booking date derive from the intact bank statement, never user-supplied amounts. Existing matched lines and unallocated equal-value debits in the same account (including other periods) block new fee posting pending investigation. One fee document, one negative treasury posting, one match and required audit are inserted atomically; identical requests replay without duplication, different evidence conflicts. Report and treasury register check the original source and flag missing or inconsistent links. This records an actual bank expense in the custody register, not a subscriber receipt, expense authorization, arbitrary balancing correction, or complete general ledger. The register stays provisional. Reversals, bundled fees, cross-period matching, unexplained bank movements and unposted external obligations remain separate work; equal-value candidate detection cannot prove the evidence is authentic. No automatic fee recognition or prior-period mutation; raw SQL guards are G1B.

## Evidenced cash count adjustments (G1A #56)

`POST /api/treasury/cash-counts/{id}/adjustment` records one signed custody adjustment per latest accepted same-day count. Independent super_admin (not counter), explicit classification, cause and evidence, exact original variance, unique reference, unchanged original ledger snapshot, no known unposted handovers/refunds or register exceptions. Negative `confirmed_cash_loss` requires independently evidenced actual loss, not missing documents or employee debt; positive `unattributed_cash_held` means cash held pending identification, never revenue or a certified liability ledger. One adjustment, one posting and required audit in one transaction. Replay is exact, never duplicates; no backdating, partial adjustment or generic balancing. Original count/review unchanged. Report checks the preceding posting snapshot and adjustment source; later legitimate postings do not invalidate the adjustment. Null new adjustment column omitted from snapshot to preserve pre-migration hashes (previous schema changes may already have made old counts stale). The register exposes recorded unattributed cash held, not an amount available to spend. Identification/reclassification, recoverable shortages, reversal, full GL and proof of completeness remain pending. This does not close the period or certify the balance. Evidence requires human verification; raw SQL guards remain G1B.
