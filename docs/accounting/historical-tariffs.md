# Historical tariff policy (ACC-08)

- Every measured interval is [period_start, period_end). Tariff start dates and end dates are inclusive. A change at the next reading date applies to the next interval.
- An approved tariff must cover the entire measured interval. Missing, partial or overlapping coverage blocks generation; no assumed 600 price and no estimated daily consumption distribution.
- Separate measured periods can have different prices in one invoice. Each generated invoice retains the source reading, tariff identity, name, dates, units, unit price and rounded amount.
- No historical invoices or readings are rewritten. Previously deactivated legacy tariffs are not presumed approved; review the schedule before deployment.
- Legacy test fixtures explicitly create a synthetic tariff; they do not seed production.
- Model-level catalog guard rejects reversed dates, overlapping approved intervals (including inclusive boundaries), conflicting restorations and stale updates. Draft tariffs may overlap until approval. Historical pricing evidence prevents repricing, deactivation, deletion and changes to start dates; closing an interval must preserve every recorded period.
- Catalog operations and historical invoice quotes acquire the same singleton transaction lock, even when no tariffs exist. API bulk operations take the catalog lock before row locks. This intentionally serializes quotes and changes for the current single tariff schedule; raw SQL imports bypass model validation and must be audited before release.
- Added SQLite-compatible catalog acceptance tests and independent MySQL worker races for concurrent approval and invoice-versus-repricing. The full ACC-08 workflow, including independent MySQL worker races, passed at commit 943ba31988ced96481568433dc76f366676999f6 (run 45460352311); later changes require fresh verification.
- Manual API issuance and Filament creation now delegate to InvoiceService, deriving all financial values and dates from measured unbilled readings. Legacy request values for amounts, dates and number are ignored; Flutter and Filament creation forms no longer accept those values. Draft editing remains distinct from posting.
- Current-price API returns null for missing or ambiguous approval, and a genuine zero price remains valid. Flutter tariff list accepts authoritative null and clears stale display; historical issuance does not depend on a current-day tariff or locally estimated amounts. Receipt summaries and WhatsApp use stored tariff evidence; legacy bills without evidence and mixed-price bills have no invented single price. The sample tariff seeder creates an unapproved draft only.
- Historical correction of a retired meter requires the original invoice's stored unit price, or (for legacy single-reading invoices with no snapshot) a uniquely approved tariff for the actual period. The operator-supplied price is confirmation, not a pricing source. The replacement stores corrected units and matching historical tariff evidence; original readings, price lines and receipts are retained. The audit log identifies which price evidence source was used. Missing coverage, inconsistent evidence and aggregate corrections of multiple readings are rejected before reversal or posting. Multi-reading correction requires a future explicit per-reading contract; no consumption is apportioned by guesswork.
- WhatsApp uses snapshot units and the retired meter code; it does not infer original meter readings from unrelated readings. Correction API returns replacement tariff lines.
