## 2. سياسة الإقفال: النطاق والزمن
- فترة مالية عامة شهرية تقويمية (مقترح يعتمد المشرف timezone محاسبية واحدة IANA، Asia/Aden خيار منطقي، ولا تتغير دون خطة انتقال؛ UTC للـ instants وتوقيت audit، UTC issuance month لـ ACC14 مستقل). من أول يوم إلى آخر يوم inclusive، ومقارنة الزمن UTC نصف مفتوحة [local start converted to UTC, next local start converted to UTC). لا استخدام timezone المتصفح. التاريخ المالي YYYY-MM-DD مستقل عن reading period وpayment_date وcreated_at ورقم المستند. لا إقفال يوم مستقبل. يمكن فتح الفترة التالية قبل إقفال السابقة إذا اكتمل gate وقواعد التسلسل؛ إقفال السابقة فقط بعد اكتمال سابقتها، بلا فجوات بعد تاريخ افتتاح معتمد. سجل غائب/متداخل/تالف => fail closed عند التفعيل.
- النطاق كل الأموال في المشروع: دفتر المشتركين والفواتير والتخصيصات، خزينة نقد/بنك، حيازة المحصلين، الأموال في الطريق، الالتزامات والنقد المحتجز، العجز والمطالبات، إثباتات المطابقة والرسوم. لا يعتبر إقفال جلسة محصل أو جرد خزينة أو اعتماد كشف إقفالاً عاماً. لا ادعاء دفتر أستاذ عام مزدوج شامل إن لم يوجد حساب مقابل مثبت لكل مصدر؛ هذا إقفال للسجل المالي المغطى فقط حتى اعتماد نموذج GL كامل إن كان مطلوباً.
- افصل occurred_on (الواقعة/تاريخ البنك الفعلي) وeffective_on (تاريخ إثبات الأثر في الفترة المفتوحة) وrecorded_at UTC (وقت تسجيل/اعتماد النظام). مصدر المستند رقم/هوية ثابتة، لا تغيير تاريخ أصل لتعويض تأخر. كل أثر مالي يربط period_id وeffective_on ومعرف عملية ثابت وأثره المالي؛ transactions حالياً لا يحمل effective_on موحداً، فلا تستنتجه من created_at. تتطلب migration وعقد provenance منفصلين بعد اعتماد B. التسوية التشغيلية المتأخرة لا تعيد كتابة التقرير المقفل. تاريخ إصدار الرقم ليس تاريخ القيد.

## 4. آلة الحالة والتنفيذ الآمن
OPEN -> FROZEN -> CLOSED (نهائي). FROZEN -> OPEN فقط بقرار إلغاء محاولة قبل اعتمادها مع سبب وسجل تدقيق وحاجز مطابق؛ لا CLOSED -> OPEN ولا زر إعادة فتح. تجهيز أولي read-only خارج الحاجز مسموح لكن non-binding. 
1. طلب إقفال بمفتاح ثابت وصلاحية مستقلة financial.period.request؛ من جهز/طلب ليس من يعتمد. قفل gate قبل كل resource؛ تحقق period/scope/sequence/time and previous closure، كل transactions قبل fence drained؛ increment epoch، حفظ attempt وتجميد الفترة atomically. إيقاف كل writer مؤثر أثناء أخذ snapshot النهائي (مقترح محافظ: fence على النطاق كله حتى اكتمال الاعتماد؛ قد يفصل لاحقاً وفق D proof)، حتى لو فترة لاحقة مفتوحة؛ لا network calls/queue waits تحت transaction. UI/CLI/API/queue/scheduler/import/restore/old workers يلتزمون جميعاً؛ لا نجاح محاسبي لطلب queued أثناء التجمد. raw SQL privileged خارج التطبيق يحتاج منع فعلي وتشغيل migration تحت maintenance fence.
2. prepare أثناء FROZEN ثابتة: تحقق invariants والـ coverage أدناه، وقائمة carry وتفاصيلها، افحص all source rows exact canonical + sequence/commit manifest، خزن candidate snapshot + hash/epoch، review by second authorized actor. لا تدخل بيانات مالية تحت اسم إعداد snapshot. إن كان الحجم كبيراً، snapshot من صفحات مفتاحية ثابتة تحت fence لا معاملة تقفل لكل فترة انتظار المستخدم؛ finalizer يعيد التحقق من version/manifest/approvals. لا الاعتماد على MAX(id) أو created_at وحده: auto increment allocation/commit order قد يختلف، soft-delete/backdating/dimensions/legacy mutable. gate+immutable source links+full deterministic manifest أساسية. فشل/timeout يبقي FROZEN حتى abort مستقل أو retry مطابق، لا يفتح تلقائياً.
3. اعتماد مستقل financial.period.approve (لا self approval، permission revalidation وactive actor، actor/role locking مع ACC10). في transaction نهائية: gate -> period -> attempt -> verify epoch/hash/coverage/carry approvals + previous snapshot/hash -> insert immutable closure/snapshot -> CLOSED وupdate fence -> required audit. لا أثر جزئي: فشل audit أو constraint أو snapshot => rollback، تظل محاولة FROZEN قابلة لإعادة المحاولة. Exact replay يرجع نفس closure read-only؛ payload مختلف 409. تحرير fence بعد commit فقط؛ إن فشل post-commit notification لا إعادة إقفال. تسجيل إجراءات attempt/abort/approve وأثرها. Queue notifications afterCommit، لا إخراج شهادة/PDF رسمي قبل commit.
4. تقارير as-of تقرأ snapshot معتمد ثابت + manifest؛ لا re-run live Payment::active أو live allocation أو current square/name. التقارير التشغيلية الحالية تبقى منفصلة بوضوح. الإقفال التالي يبدأ closing السابقة + movements الجديدة (including resolved carries). نسخ احتياطية/استعادة مع fence وفحص سلسلة hashes والبيانات اللاحقة/الأرقام الصادرة؛ فقد الأدلة => عدم إعادة فتح الكتابة قبل استعادة موثوقة.

## 5. بوابات الإقفال وثوابت المبالغ
| القطاع | معادلة/شرط القبول | سبب منع الإقفال |
|---|---|---|
| المشترك/الفواتير | opening signed ledger + signed event movements = closing؛ debt=max(-net,0), credit=max(net,0) لكل مشترك ثم جمع؛ الفاتورة قيمة استهلاك جديدة فقط؛ كل مصدر/قيد مطابق؛ current allocation revision as-of محفوظة | missing/duplicate/orphan/invalid reversal; مبلغ أو cache خارج الحد؛ قيد مجهول |
| التخصيص | لكل مصدر متاح=مخصص+فائض؛ مجموع الفاتورة لا يتجاوز أصلها؛ target/replacement ثم FIFO معتمد؛ revision تاريخية immutable | drift، عدم conservation، تعديل تاريخي غير مثبت |
| النقد | opening physical custody + verified cash in - verified cash out = recorded closing؛ جرد عند cut-off مع إثبات؛ الحيازة موزعة بين الخزينة والمحصل/النقل | فرق غير مثبت، تسليم/تمويل مفقود، صندوق مفتوح غير محسوب |
| البنك | opening book + signed postings=closing book؛ opening statement + lines=closing statement؛ الفرق = opening diff + unmatched bank - unmatched ledger؛ فرق غير مفسر=0 | كشف ناقص/متداخل/بصمة تالفة أو خصم بلا أصل مثبت؛ لا إخفاء unmatched by net |
| التحويلات | dispatched=received+returned+transit fees+approved loss/reclass+remaining؛ remaining>=0؛ cross-period carry unique | رصيد غير محفوظ، تحويل مفقود، إخطار فشل بلا رد مثبت |
| العهد | opening custody + actual funds/collections - verified handover/spend/transfers = closing custody؛ لا funding مرتين | عهدة مجهولة/فرق غير مثبت |
| الالتزامات | opening liability + holds - verified releases/reclass=closing liability؛ cash available=recorded cash - distinct restricted cash؛ لا عد مزدوج | فائض مجهول بلا liability، negative/corrupt hold، إنفاق محجوز |
| تدقيق/تغطية | كل مصدر محتمل وقيوده وتخصيصه/تسويته مطابق؛ أذونات مستقلة؛ كل تقرير محدد scope/timezone/period | أي write path غير محروس، مصادر غير مغطاة، أثر قابل للتلاعب، migration/host غير معتمد |
