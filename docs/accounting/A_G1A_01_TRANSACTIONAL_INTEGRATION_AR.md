## 2. حدود المال قبل الترحيل
M = مبلغ الشيك الأصلي بوحدة minor؛ قيمة DECIMAL(12,2) في payments.amount وtransactions.amount وinvoices.amount_paid/total_amount وsubscribers.balance تعني 1 <= M <= 999999999999 (9,999,999,999.99 رئيسية). bank parser الحالي يقبل 12 خانة صحيحة (حتى 99,999,999,999,999 minor) وtreasury_postings.amount_minor BIGINT signed؛ لا نستخدم الحد الأوسع للشيك. حد PHP_INT_MAX المختبر في المخطط المعزول ليس حد منتج. يجب تضييق contract قبل adapter إلى حد أضيق حقل، وفحص aggregate/cache overflow قبل كل تغيير، لا clamp. meters.balance DECIMAL(10,2) => abs <= 9999999999 minor (99,999,999.99 رئيسية) عند لزوم تحديث cache العداد التاريخي؛ check preflight, إما خطة توسيع معتمدة أو رفض العملية بلا آثار. cash_sessions DECIMAL(14,2) ليس مجال عكس الشيك؛ cash_session_id null. مجموعات تخصيص BIGINT unsigned/أرصدة الخزينة تحتاج checked add/subtract، لا cast unsigned أكبر من int؛ جميع حدود قاعدة البيانات والـ Dart web/API وتبادل JSON تحت عقد ACC-09 (لا float في التخطيط أو تحويل DECIMAL/المقارنة، تحويل string exact إلى minor ومنه string DECIMAL). لا تنشر حتى قبول ACC-09 في المسارات المعنية. لا تعتمد rounding لإخفاء فرق minor واحد. جميع الأمثلة الاصطناعية فقط.

## 3. اختيار سجل مستقل وحماية المصدر
تصميم إضافي مقترح، أسماء مبدئية بعد حجز المسارات:
- treasury_collection_returns: id, payment_id UNIQUE FK RESTRICT, treasury_bank_collection_id UNIQUE FK RESTRICT, original_payment_transaction_id UNIQUE FK RESTRICT, original_credit_line_id FK RESTRICT, return_line_id UNIQUE FK RESTRICT, treasury_account_id/subscriber_id FK RESTRICT, instrument identity, amount_minor UNSIGNED BIGINT + CHECK 1..999999999999, bank booked_on, accounting effective_on, period_id FK, request_uuid UNIQUE canonical lowercase، reference UNIQUE normalized، approved_by/requested_by FK RESTRICT, bank evidence/link evidence، canonical payload SHA256/version. لا تعديل/حذف بعد إدراج؛ لا stored flag من العميل؛ إثبات تاريخي immutable. كل علاقة تطابق الهوية والمبالغ ومرجع التحصيل الأصلي.
- treasury_postings: nullable UNIQUE FK treasury_collection_return_id، kind=bank_collection_return, amount_minor=-M، effective_on معتمد، evidence_reference = normalized reference. جميع أنواع المصدر mutually exclusive؛ تضاف حراسة كل validators الخاصة بالأنواع القديمة لمنع coexistence. bank_statement_matches الموجود unique لكل line/posting؛ لا فك القيد في المرحلة الأولى.
- treasury_collection_return_effects: return_id UNIQUE FK RESTRICT, reversal_transaction_id UNIQUE FK RESTRICT، treasury_posting_id UNIQUE FK RESTRICT، match_id UNIQUE FK RESTRICT، allocation_revision_id FK RESTRICT، audit_event_id (إن سمح العقد) FK RESTRICT، أثر ثابت بعد commit. ربط claim/late source إلزامي عند وجوده: provenance نوع/معرف محفوظ منذ clearance (أو إثبات مصدر legacy مصرح، لا fallback صامت). لا حذف/تعديل السند الأصلي أو تحويل claim cleared إلى rejected. حالة returned مشتقة من return + effects الصحيحة، لا voided_at ولا refund.
- خيار ledger الأول: إعادة استخدام نوع payment_reversal (reference_type=Payment::class, reference_id=original payment id) بقيد فريد أو registry ضمان واحد عبر كل مسارات العكس؛ ربطه بمستند ارتجاع مستقل via effects. ميزة: تقارير FinancialReportingService تعرض reversals حالياً. لكن TransactionService::reverseDocument الحالي لا يميز السبب ولا يدعم عقد exact؛ يلزم entry point محروس يقبل مستنداً مثبتاً لا إدراج مباشر. لا اعتماد على polymorphic reference كـFK وحيد. لا نستخدم generic void لتجاوز منع الإلغاء. بديل type مستقل يتطلب تحديث كل consumers وتقارير/UI/mobile؛ لا يخلط النوعان. القرار المطلوب من المشرف: اعتماد reuse + linkage أو dedicated type. تصميم هذا الملف يفترض reuse + linkage.
- قبل القيد: افحص الأصل غير محذوف (withTrashed)، حركة payment واحدة فعالة +M وهوية مشترك/عداد/retired meter مطابقة، لا reversal سابق/voided/pending void/refund/account transfer/closed correction (أو علاقات عكسية)/حالة مركبة؛ لا حساب مرتبط بصندوق. لا تعكس سند legacy بلا إثبات هوية. جمع المرجع مع domain references تحت lock (treasury_postings.evidence_reference unique، سائر الجداول)، ACC14 يحدد رقم المستند إن تقرر رقم رسمي؛ UUID/مرجع دليل لا يعد رقم سند جديد. على MySQL/SQLite قيود FK/check/unique + append-only guards وفق ACC-10/G1B واختبار صلاحيات الاستضافة المسموحة؛ لا محاولة تفعيل غير مدعومة أو تعديل إنتاجي. ترقية additive فقط، لا backfill وهمي، dry-run synthetic، عدم إسقاط الأدلة عند rollback؛ عند فشل DDL احتفظ بالمخطط الجزئي واعمل forward repair بعد inventory؛ لا تشغيل تلقائي قبل تحقق قيود الحماية.
