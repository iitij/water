# 0. كيف تُقرأ هذه الوثيقة

## 0.1 الغرض

هذه الوثيقة هي **المصدر الوحيد للحقيقة (Single Source of Truth)** لمشروع تطبيق الموبايل. أي قرار يخالف ما ورد فيها يجب أن يُسجَّل كـ ADR (سجل قرار معماري) ويُعتمد من قائد التقنية قبل التنفيذ. الهدف منها أن يفتح أي مطور الملف ويعرف بدقة:

1. ما الموجود في النظام الحالي بالتفصيل (وليس بشكل عام).
2. ما الذي يجب بناؤه في الـ API والسبب.
3. كيف يُبنى تطبيق Flutter معمارياً وتصميمياً.
4. ما المهمة الموكلة إليه، وما حدودها، وما معيار إنجازها.
5. كيف يستعمل الوكلاء (Agents/Subagents) لتسريع عمله دون إفساد النظام.

## 0.2 اصطلاحات الأولوية

| الرمز | المعنى | القرار |
|---|---|---|
| **P0** | أساسي لقيام التطبيق | لا يُسلَّم الإصدار بدونه |
| **P1** | مهم جداً | يُسلَّم في الإصدار الأول إن أمكن، وإلا في 1.1 |
| **P2** | تحسين | يُؤجَّل إلى 1.2 أو ما بعده |

## 0.3 اصطلاحات فنية

- **Parity**: تكافؤ الوظائف بين لوحة الويب والتطبيق. هدفنا **Parity 100%** على مستوى العمليات، و**Parity 90%+** على مستوى إدارة النظام.
- **Offline-first**: التطبيق يعمل بلا إنترنت في العمليات الميدانية (قراءة العدادات، التحصيل) ثم يزامن.
- **Contract-first**: يُكتب عقد OpenAPI أولاً، ويُبنى الـ Backend والـ Flutter بالتوازي عليه.
- **DoD / DoR**: تعريف الإنجاز وتعريف الجهوزية (القسم 7.7).

## 0.4 خريطة الملفات المرجعية في المستودع

| المسار | ما يمثله |
|---|---|
| `app/Filament/Resources/*` | كل شاشات وعمليات لوحة التحكم (المصدر الحقيقي للميزات) |
| `app/Services/*` | منطق العمل المالي (فوترة، تحصيل، قراءات، تصدير، واتساب) |
| `app/Models/*` | نموذج البيانات وقواعد الأحداث (Model Events) |
| `app/Http/Controllers/Api/*` | الـ API الحالي (ناقص) |
| `routes/api.php` | 20 مساراً فقط |
| `database/migrations/*` | المخطط الفعلي (48 ملف هجرة) |
| `resources/views/pdf/*` | قوالب PDF للفاتورة وسند القبض |
| `database/seeders/*` | الأدوار والبيانات الأولية |

# 1. الملخص التنفيذي

## 1.1 المشكلة

النظام الحالي مبني على **Laravel 13 + Filament 5.6** ويعمل بكفاءة على المتصفح، لكن العاملين الميدانيين (قارئ العداد، المحصّل) لا يستطيعون استخدامه بفاعلية على الهاتف: لوحة Filament ثقيلة، تحتاج اتصالاً مستمراً، غير مصممة للشاشات الصغيرة، ولا تدعم العمل بلا شبكة في المناطق ذات التغطية الضعيفة. كذلك فإن الـ API الحالي لا يغطي إلا جزءاً صغيراً من وظائف النظام (20 مساراً مقابل أكثر من 90 عملية في اللوحة)، وبدون صلاحيات ولا مزامنة ولا رفع صور فعّال.

## 1.2 الحل

بناء **تطبيق Flutter واحد** (Android / iOS / Web / Windows / macOS) يغطي كل عمليات النظام، مع:

1. **إعادة بناء طبقة API كاملة (`/api/v1`)** بـ 90+ نقطة نهاية، مصممة للهاتف: ترقيم صفحات، مزامنة تفاضلية، مفاتيح عدم تكرار، صلاحيات، PDF، إشعارات.
2. **تطبيق Flutter بـ Clean Architecture** (Riverpod + go_router + Dio + Drift) مع **Offline-first** في العمليات الميدانية.
3. **نظام تصميم عربي RTL حديث** قابل للتكيّف من 320dp إلى 1440dp، مع الوضع الليلي، ودعم تكبير الخط، وإمكانية وصول كاملة.
4. **تقسيم عمل واضح** لـ 7–8 أشخاص، و**استراتيجية وكلاء (Agents)** لرفع سرعة التسليم دون المساس بجودة أو أمان النظام المالي.

## 1.4 النتيجة المتوقعة

- **تكافؤ وظيفي 100%** مع لوحة الويب في العمليات اليومية (قراءة، فوترة، تحصيل، إدارة مشتركين)، و**95%** في إدارة النظام.
- **إدخال قراءة في أقل من 20 ثانية** (بحث/مسح → قراءة → حفظ) مقابل ~60–90 ثانية على المتصفح.
- **تحصيل في أقل من 25 ثانية** مع سند قبض ورقمي ومشاركة واتساب.
- **عمل كامل بلا إنترنت** لمدة يوم عمل كامل مع مزامنة تلقائية.
- نسبة أخطاء إدخال أقل من 2% بفضل التحقق الفوري (القراءة السابقة، الاستهلاك، حالة الفاتورة).
- تطبيق سريع: بدء بارد < 2.5 ثانية على جهاز متوسط، 60/120fps، حجم تنزيل < 30MB لأندرويد.

## 1.5 المدة والفريق

- **الفريق الموصى به:** 8 أشخاص (قائد تقنية، مطور Backend أول، مطور Backend ثانٍ/QA API، 3 مطوري Flutter، مصمم UI/UX، QA موبايل + DevOps بدوام جزئي).
- **الفريق الأدنى المقبول:** 5 أشخاص مع تمديد المدة إلى 18–20 أسبوعاً.
- **المدة:** 14 أسبوعاً (Sprint 0 لمدة أسبوع + 6 سبرنتات × أسبوعين + أسبوع تثبيت وإصدار) حتى الإصدار العام.
- **الإصدار التجريبي (Internal Beta):** الأسبوع 9. **الإصدار العام:** الأسبوع 14.

- لا توجد `openapi.yaml` ولا توثيق API.

## 2.3 قواعد العمل الحرجة

هذه القواعد هي «قانون» النظام. **أي شاشة في التطبيق يجب أن تحترمها، وأي مطور يجب أن يعرفها حرفياً.**

| # | القاعدة | المرجع | الأثر على التطبيق |
|---|---|---|---|
| BR-01 | الرصيد الموجب = دائن (credit) للمشترك، السالب = مدين (debt). لا يُعرض الرصيد السالب كعدد سالب في واجهة المستخدم، بل يُعرض «مستحق: X» و«دائن: Y». | `Subscriber::getOutstandingBalance` | تنسيق موحّد في `MoneyText`. |
| BR-02 | الحساب المالي معزول: فاتورة/دفعة بـ`meter_id` لا تتداخل مع حساب المشترك (`meter_id = null`). | `PaymentService::recalculateInvoices` | أي شاشة تحصيل تفسّر «المستحق» حسب الحساب المحدد. |
| BR-03 | الدفعة تُطبَّق أولاً على الفاتورة المحددة ثم FIFO على الأقدم. | `PaymentService::distributePayment` | واجهة الدفع تعرض أثر التوزيع قبل التأكيد. |
| BR-04 | المبلغ الزائد عن كل الفواتير يبقى رصيداً دائناً (لا يُفقد). | `TransactionService` | إظهار «رصيد دائن متبقٍ» في السند. |
| BR-05 | «المتبقي الحقيقي» للفاتورة الأحدث تراكمي (يشمل الفواتير الأقدم من نفس النوع/العداد). | `getTrueRemainingAmount` | شاشة التحصيل تعرض: متبقي هذه الفاتورة + إجمالي المستحق. |
| BR-06 | «المتأخرات السابقة» عنصر عرض ولا يُضاف إلى `total_amount` لتفادي الازدواج. | `InvoiceService` سطر 8 | لا تحسب الإجمالي في التطبيق، اعرض القيمة من الـ API. |
| BR-07 | الفاتورة تُصدر فقط إذا وُجد استهلاك غير مفوتر أو رسوم اشتراك/وايت مستحقة، وإلا يرمي النظام استثناءً عربياً واضحاً. | `InvoiceService` | ترجمة الخطأ إلى رسالة ودّية + اقتراح إجراء. |
| BR-08 | حالة الفاتورة للأحدث تُحسب تراكمياً، وللأقدم تُحسب على الفاتورة نفسها. | `Invoice::updateStatus` | لا تعِد حساب الحالة في العميل. |
| BR-09 | `grace_period` (افتراضي 14 يوماً) يحدد انتقال الفاتورة إلى `overdue`. | `updateStatus` | عدّاد «متبقي X يوم» في واجهة الفاتورة. |
| BR-10 | دورة القراءة: `monthly` / `half_monthly` / `ten_days` / `weekly`، ويوم القراءة `last_day` أو رقم يوم. | `ReadingService` | شاشة القراءة تعرض الفترة المقترحة ولا تسمح بتعديلها إلا بصلاحية. |
| BR-11 | فترة القراءة تبدأ من اليوم التالي لآخر `period_end`، وأول فترة تبدأ من `subscription_start_date`. | `calculateReadingPeriod` | عند مشترك جديد بدون تاريخ بدء، تُستخدم بداية الشهر. |
| BR-12 | لا يمكن إدخال قراءتين لنفس الفترة لنفس العداد. | `ReadingController@store` | التطبيق يجب أن يمنع مسبقاً ويعرض سبباً. |
| BR-13 | القراءة الحالية ≥ القراءة السابقة وإلا خطأ 422. | `ReadingController@store` | تحقق فوري في الحقل + تحذير بصري. |
| BR-14 | لا يمكن حذف/تعديل قراءة مفوترة. | `Reading::booted` | إخفاء الأزرار وإظهار السبب. |
| BR-15 | عند تفعيل `auto_issue_invoice_on_reading` تُصدر الفاتورة تلقائياً بعد الحفظ. | `ReadingSettings` | التطبيق يعرض شاشة «تم إصدار الفاتورة» مع إمكانية المشاركة. |
| BR-16 | أرقام الفواتير والسندات تُولَّد على السيرفر فقط وبصيغة شهرية متسلسلة. | `generateBillNumber` / `generateReceiptNumber` | **ممنوع** توليدها في العميل، حتى في وضع عدم الاتصال (يُخصص رقم مؤقت وسند «معلّق»). |
| BR-17 | حذف الفاتورة يفك ارتباط القراءات والرسوم والطلبات والدفعات ويعيد التوزيع. | `Invoice::deleted` | في التطبيق: «إلغاء/حذف» يتطلب صلاحية وتأكيداً مزدوجاً. |
| BR-18 | كل تغيير مالي يُسجَّل في `transactions` ويُحدّث الأرصدة الكاش. | `TransactionService` | لا حساب أرصدة في العميل كمصدر حقيقة. |
| BR-19 | الإعدادات تُقرأ من `settings` وتؤثر مباشرة على الفواتير والرسائل. | `Setting::get` | التطبيق يحمّل الإعدادات مرة عند البدء ويحدّثها عند تغييرها. |
| BR-20 | القوالب النصية (واتساب) تستخدم Placeholders وشرط `{if:key}...{/if:key}`. | `WhatsAppService`, `SettingController` | معاينة القالب قبل الإرسال. |

# 3. الرؤية والمنتج وتجربة المستخدم

## 3.1 الشخصيات والأدوار

النظام يعتمد 4 أدوار أساسية (مع إمكانية إضافة `supervisor`). كل دور له تطبيق «داخلي» بواجهة مختلفة (نفس التطبيق، تنقّل وصلاحيات مختلفة).

### 3.1.1 مدير النظام (`super_admin` / `admin`)

- **الوصف:** صاحب المشروع أو المدير المالي.
- **البيئة:** مكتب، هاتف متوسط/فاخر، شبكة جيدة.
- **ما يريده:** صورة كاملة عن التحصيل والمتأخرات، إصدار فواتير، متابعة أداء المحصلين والقراء، تعديل الإعدادات والسياسات.
- **نقاط الألم:** لوحة التحكم على الهاتف صعبة، وتقارير Excel غير متاحة أثناء التنقل.
- **مؤشر النجاح:** يفتح التطبيق 3–5 مرات يومياً ويجد كل رقم في ≤ 3 نقرات.

### 3.1.2 المحصّل (`collector`)

- **الوصف:** يزور المشتركين ويحصّل نقداً/حوالات.
- **البيئة:** الشارع، شبكة متقطعة، هاتف متوسط، استخدام بيد واحدة، غالباً في الشمس (يحتاج تبايناً عالياً).
- **ما يريده:** يعرف فوراً كم على المشترك، يسجل الدفعة في 20 ثانية، يطبع/يرسل سنداً، ويكمل بلا شبكة.
- **نقاط الألم الحالية:** فتح المتصفح، تسجيل دخول، بحث بطيء، فقدان الدفعة عند انقطاع الشبكة.
- **مؤشر النجاح:** 30+ سنداً يومياً، صفر سندات مفقودة، صفر دفعات مكررة.

### 3.1.3 قارئ العداد (`meter_reader`)

- **الوصف:** يقرأ العدادات شهرياً.
- **البيئة:** ميدان، حرارة، شبكة ضعيفة، قفازات أحياناً (أزرار كبيرة).
- **ما يريده:** يمسح QR العداد أو يبحث برقم المسار، يدخل القراءة، يأخذ صورة، ينتقل للتالي. لا يريد نماذج طويلة.
- **مؤشر النجاح:** 80–120 قراءة يومياً، متوسط < 20 ثانية للقراءة، نسبة خطأ < 1%.

### 3.1.4 مشرف (`supervisor`) — اختياري P1

- **الوصف:** يشرف على فريق ميداني.
- **ما يريده:** متابعة تقدّم القراءات والتحصيل حسب المربع والمستخدم، وإعادة تعيين مهام.
- **ملاحظة:** حالياً غير موجود كدور، لكن التطبيق يُصمَّم ليضيفه دون تغيير معماري.

### 3.1.5 المشترك (خارج النطاق الأول)

- **P2:** تطبيق/وضع للمشترك: فواتيره، رصيده، سنداته، طلب وايت، شكوى. البنية التحتية للـ API ستجهَّز له من الآن (مصادقة بالهاتف + OTP لاحقاً).

## 3.2 رحلة المستخدم لكل دور

### 3.2.1 رحلة «إدخال قراءة» (قارئ العداد)

```
[فتح التطبيق 1.2s]
   ↓ (جلسة محفوظة — لا تسجيل دخول)
[الشاشة الرئيسية: مهام اليوم / عدد القراءات المتبقية]
   ↓ زر «قراءة جديدة» (FAB كبير)
[مسح QR أو بحث: مربع/مسار / رقم العداد / اسم المشترك]
   ↓ (نتيجة واحدة → انتقال مباشر)
[شاشة القراءة: القراءة السابقة + الفترة + المبلغ المتوقع]
   ↓ إدخال الرقم (لوحة أرقام كبيرة، تحقق فوري)
[الاستهلاك = 42 وحدة × 600 = 25,200 ريال]  ← حساب معاينة فقط
   ↓ (اختياري) صورة العداد
[حفظ]
   ↓ (إذا auto-issue) شاشة نجاح: «تم إصدار الفاتورة INV-202610-0142»
   ↓ [مشاركة واتساب] [قراءة تالية]
```

**نقاط حرجة:** يجب أن يعمل كل هذا بلا شبكة. عند عدم الاتصال يظهر شريط «محفوظ محلياً — سيُزامن» ويُخزَّن في قائمة الانتظار مع UUID.

### 3.2.2 رحلة «تحصيل» (المحصّل)

```
[الرئيسية: «مستحق اليوم» + زيارات مجدولة]
   ↓ بحث بالاسم/الهاتف/رقم المسار (بحث فوري محلي)
[ملف المشترك: ملخص المستحق + الفواتير غير المسددة]
   ↓ زر «تحصيل» (أخضر كبير)
[شاشة الدفع: المبلغ المقترح = المتبقي، طرق دفع، مرجع، «وذلك مقابل»]
   ↓ تأكيد (سحب للإتمام)
[نجاح: سند REC-202610-0093 — عرض/مشاركة/طباعة]
   ↓ [تحصيل آخر] [الرجوع]
```

**قاعدة:** إذا كان المبلغ المدخل > المتبقي، يظهر تنبيه «سيتبقى 3,000 ريال كرصيد دائن — متابعة؟».

### 3.2.3 رحلة «متابعة مالية» (المدير)

```
[الرئيسية: تحصيل الشهر، المتأخرات، فواتير غير مدفوعة]
   ↓ الرسم البياني → تقرير التحصيل
   ↓ «فواتير متأخرة» → قائمة مفلترة → تفاصيل → اتصال/واتساب/تحصيل
   ↓ «تقارير» → تصدير Excel → مشاركة
```

### 3.2.4 رحلة «إعدادات/تغيير سياسة»

مدير → المزيد → الإعدادات → مجموعة (الفوترة/السند/القراءة/الرسائل) → تعديل → معاينة → حفظ → تُبطل ذاكرة الإعدادات ويُحدَّث كل التطبيق.

### 3.3.1 معايير نبرة الكتابة (Microcopy)

- عربية فصحى مبسطة، جمل قصيرة، أفعال مباشرة: «حفظ القراءة»، «تحصيل 12,500 ريال».
- لا مصطلحات تقنية للمستخدم: «تعذّر الاتصال — سيُحفظ محلياً» بدل «DioException».
- الأرقام دائماً بفواصل آلاف ورقمين عشريين: `12,500.00`.
- العملة: «ريال» في النصوص، والرمز `ر.ي` في الأرقام المضغوطة.
- التواريخ: `23 أكتوبر 2026` في العرض، `2026-10-23` في الإدخال/الـ API.

## 3.6 المواصفات التفصيلية للشاشات

> لكل شاشة: الهدف، البيانات، المكوّنات، الحالات، الأخطاء، الصلاحية، معيار القبول. هذه المواصفات ملزمة للمطور والمصمم.

### 3.6.1 A1 — Splash / التهيئة

- **الهدف:** تحميل الإعدادات المحلية، التحقق من الجلسة، توجيه.
- **السلوك:** ≤ 1.5 ثانية (لا تنتظر الشبكة؛ اعرض النسخة المحلية وحمّل التحديث في الخلفية).
- **الحالات:** جلسة صالحة → Home؛ لا جلسة → Login؛ إصدار قديم → شاشة تحديث إجباري (من `app_min_version`)؛ صيانة → شاشة صيانة.
- **معيار القبول:** لا شاشة بيضاء > 300ms؛ يعمل بلا شبكة.

### 3.6.2 A3 — تسجيل الدخول

- **الحقول:** البريد الإلكتروني (LTR)، كلمة المرور (إظهار/إخفاء)، «تذكرني» (افتراضي مفعّل)، «الدخول بالبصمة» إن سبق الدخول.
- **الأزرار:** دخول (Primary، ارتفاع 52)، نسيت كلمة المرور (P1)، رقم الدعم.
- **التحقق:** بريد صالح، كلمة مرور ≥ 6.
- **الأخطاء:** 422 → رسالة عربية تحت الحقل؛ 429 → «محاولات كثيرة، انتظر دقيقة»؛ 401 → «بيانات غير صحيحة»؛ شبكة → «تحقق من الاتصال» مع إعادة.
- **الأمان:** لا حفظ كلمة المرور؛ التوكن في `flutter_secure_storage`؛ خيار القفل البيومتري بعد أول دخول.
- **معيار القبول:** دخول ≤ 3 ثوانٍ، رسائل خطأ مفهومة، لا انهيار عند JSON غير متوقع.

### 3.6.3 A6 — القفل البيومتري

- يظهر عند العودة للتطبيق بعد ≥ 5 دقائق (قابل للضبط).
- زر «استخدام كلمة المرور» كبديل.
- لا يُقفل أثناء عملية دفع جارية.

### 3.6.4 B1 — الرئيسية (Home)

**مدير:**
- رأس ترحيبي + اسم المشروع + شعار + زر إشعارات (شارة).
- 4 مؤشرات (2×2): مشتركون، قراءات الشهر، تحصيل الشهر، متأخرات.
- بطاقة «تحصيل آخر 6 أشهر» (رسم أعمدة/خط).
- «تحتاج انتباهك»: فواتير متأخرة، قراءات غير مفوترة، طلبات وايت مكتملة غير مفوترة (قائمة قابلة للنقر).
- اختصارات: إصدار فاتورة، تحصيل، تقارير.
- آخر العمليات (آخر 5).

**محصّل:**
- «مستحق اليوم» (إجمالي) + عدد المشتركين المدينة.
- زر التحصيل الكبير.
- آخر 5 سندات.
- قائمة «متابعة» (مشتركون بمواعيد اليوم — إن أُضيفت الجدولة P2).

**قارئ:**
- «مهام اليوم»: عدد العدادات المتبقية في المربع المخصص.
- شريط تقدّم دائري.
- زر «قراءة جديدة» كبير.
- آخر القراءات + حالة المزامنة.

- **الحالات:** تحميل (Skeleton)، خطأ (بطاقة إعادة محاولة مع الاحتفاظ بالبيانات المخزنة)، فارغ (رسوم توضيحية).
- **الصلاحية:** البيانات تُبنى من `/dashboard/summary` الذي يعيد ما يخص الدور.
- **معيار القبول:** كل الأرقام تطابق `AdminController@stats`؛ لا رقم يُحسب في العميل؛ التحميل < 1.5s على 3G.

### 3.6.5 B4 — البحث الشامل

- يبحث في: المشتركين، العدادات، الفواتير، السندات (حسب الصلاحية).
- بحث محلي فوري (Drift) + بحث سيرفر عند عدم وجود نتيجة محلية.
- يفسّر المدخلات الذكية: `4/12` = مربع 4 مسار 12؛ رقم يبدأ بـ `INV` = فاتورة؛ `REC` = سند؛ 11 رقماً = هاتف.
- **معيار القبول:** نتيجة ≤ 400ms، يظهر نوع النتيجة وسبب المطابقة.

### 3.6.6 C1 — قائمة القراءات

- **الفلاتر:** الكل / غير مفوترة / مفوترة / الشهر الحالي / مربع / قارئ.
- **العناصر:** رقم العداد، المشترك، الفترة، القراءة (سابقة → حالية)، الاستهلاك، حالة الفوترة، من أدخلها.
- **الإجراءات:** فتح، إصدار فاتورة (للمفوتر: معطّل مع سبب)، حذف (غير مفوتر فقط).
- **الإجراء الجماعي:** تحديد غير المفوترة → «إصدار الفواتير» → معاينة النتائج → تنفيذ → تقرير نجاح/أخطاء.
- **معيار القبول:** منع تحديد قراءة مفوترة (رسالة واضحة)، معالجة أخطاء كل عداد على حدة.

### 3.6.7 C2–C3 — مسح QR / بحث العداد

- مسح `unique_code` (QR يحوي `WTR:M:<id>:<code>` أو الرقم فقط).
- كاميرا مع إطار، فلاش، إدخال يدوي بديل.
- نتائج البحث: بطاقة عداد (رقم، مشترك، مربع، مسار، آخر قراءة، حالة).
- **معيار القبول:** مسح ≤ 2 ثانية، دعم QR/Barcode، لا يمسح رموزاً غير عدادات.

### 3.6.8 C4 — إدخال قراءة (الشاشة الأهم)

**البيانات المحمّلة مسبقاً من `/meters/{id}/period`:**
- المشترك، المربع، رقم العداد/المسار، آخر قراءة، القراءة السابقة، فترة القراءة (من/إلى)، سعر الوحدة الفعّال، وجود رسوم اشتراك/وايت مستحقة، تفعيل الإصدار التلقائي.

**العناصر:**
1. بطاقة تعريف العداد (ثابتة أعلى).
2. الفترة (قابلة للمراجعة، مقفلة افتراضياً).
3. «القراءة السابقة: 1,240» (لا تُعدَّل إلا بصلاحية مدير).
4. حقل «القراءة الحالية» (تركيز آلي، لوحة أرقام).
5. شريط حساب مباشر: «الاستهلاك: 42 وحدة × 600 = 25,200 ريال».
6. صورة العداد (اختياري/إلزامي حسب إعداد).
7. مفاتيح: إضافة رسوم اشتراك (مع المبلغ المجمّع)، إضافة رسوم وايت (مع المجموع).
8. ملاحظات.
9. زر «حفظ»، و«حفظ + التالي».
10. تحذير عدم الاتصال.

**التحقق الفوري:**
- فارغ → خطأ.
- أقل من السابق → خطأ مانع مع الفرق.
- مساوٍ للسابق → تحذير «استهلاك صفر — متابعة؟».
- زيادة > 300% عن متوسط آخر 3 قراءات → تحذير تأكيدي (احتمال خطأ إدخال).
- فترة مكررة → خطأ مانع مع التاريخ.

**النجاح:** إن كان الإصدار التلقائي مفعّلاً تظهر شاشة C5 بملخص الفاتورة وأزرار (عرض/واتساب/التالي). وإلا: Snackbar + عودة.

**Offline:** يُحفظ في `pending_mutations` مع `client_uuid`، ويظهر «محفوظ محلياً»؛ يُزامن تلقائياً ويعرض شارة.

**معيار القبول:**
- إدخال قراءة صحيحة ≤ 20 ثانية (قياس على 5 مستخدمين).
- لا يمكن إنشاء قراءتين لنفس الفترة حتى بلا شبكة (فحص محلي).
- لا يمكن إرسال قراءة أقل من السابقة حتى لو تغيّر السيرفر (فحص عند المزامنة).

### 3.6.9 C7 — إصدار فواتير جماعي

- اختيار قراءات غير مفوترة (تحديد الكل للمربع).
- معاينة: عدد الفواتير المتوقعة، إجمالي المبالغ، العدادات المتأثرة.
- تنفيذ تدريجي مع شريط تقدم (لا تجميد الشاشة).
- تقرير: نجح X / فشل Y مع السبب لكل فاشل + تصدير/مشاركة.
- **معيار القبول:** عملية 100 قراءة ≤ 30 ثانية (على السيرفر)؛ لا تجميد؛ إمكانية الإلغاء.

### 3.6.10 D1–D5 — العدادات

- D1: بحث + فلاتر (مربع، حالة، وجود قراءة هذا الشهر)، عناصر تعرض الرصيد والحالة.
- D2: تفاصيل: بيانات العداد، المستأجر، آخر 6 قراءات (رسم خطي)، الفواتير، الرصيد، أزرار (قراءة، فاتورة، QR).
- D3: نموذج: رقم العداد (فريد)، مربع (من المشترك)، مسار (فريد داخل المربع)، مستأجر، هاتف، حالة، قراءة أولية، تاريخ تركيب.
- D5: بطاقة QR قابلة للطباعة/المشاركة (توليد صورة QR محلياً).
- **معيار القبول:** تحقق المسار الفريد قبل الحفظ + رسالة عربية مطابقة للسيرفر.

### 3.6.11 E1–E9 — المشتركون وملف 360

**E1 قائمة:** بحث بالاسم/الهاتف/رقم العداد/المسار، فلاتر (مربع، حالة، عليه متأخرات)، عدّاد نتائج، تمرير لا نهائي (per_page=25). كل عنصر: الاسم، المربع، الهاتف، شارة الحالة، المتبقي/الدائن.

**E2 ملف 360** — التبويبات:
1. **نظرة عامة:** بيانات الاتصال (اتصال/واتساب/خرائط)، المربع، التاريخ، حالة الاشتراك، بطاقة أرصدة (دائن/مدين للمشترك + لكل عداد).
2. **الفواتير:** قائمة + حالة + متبقي + إجمالي؛ إصدار جديد.
3. **الدفعات:** سندات + PDF.
4. **العدادات:** قائمة + إضافة + قراءة.
5. **رسوم الاشتراك:** قائمة + إضافة + فوترة.
6. **الوايت:** طلبات + إضافة + فوترة.
7. **كشف الحساب:** حركات مرتبة زمنياً (فاتورة/سند/تسوية) مع رصيد بعد كل حركة.
8. **الحركات (Ledger)** للمدير.

**الإجراءات السفلية:** تحصيل، إصدار فاتورة، تعديل.
**معيار القبول:** كل تبويب يحمّل مستقلاً (Lazy) ≤ 700ms؛ لا N+1 في الـ API؛ مجموع الفواتير = المتبقي المعروض في الرأس.

### 3.6.12 E4 — كشف حساب

- فلاتر تاريخ (افتراضي: السنة الحالية/الكل).
- أعمدة: التاريخ، النوع، المرجع، البيان، مدين، دائن، الرصيد.
- إجماليات أعلى/أسفل.
- مشاركة PDF/Excel (P1).
- **معيار القبول:** مطابقة تامة `SubscriberController@statement` بعد إصلاح G-07.

### 3.6.13 F1 — قائمة الفواتير

- تبويبات: الكل / غير مسددة / متأخرة / مسددة / مسودات.
- فلاتر: النوع (عداد/اشتراك/وايت)، المربع، الفترة، المشترك.
- العنصر: رقم الفاتورة، المشترك/المسار، التاريخ، الإجمالي، المسدد، المتبقي، شارة الحالة.
- إجراءات سحب: PDF، واتساب، تحصيل.
- **معيار القبول:** قائمة 1000 فاتورة تتصفح بسلاسة (pagination + cached images none).

### 3.6.14 F2 — تفاصيل الفاتورة

- رأس: رقم، حالة، تاريخ، فترة، المشترك/العداد.
- ملخص مالي: استهلاك، اشتراك، وايت، متأخرات (عرض)، رصيد مخصوم، **الإجمالي المستحق** (من السيرفر)، المسدد، المتبقي (هذه الفاتورة + التراكمي).
- البنود (invoice_items).
- القراءات المرتبطة (سابقة/حالية/وحدات/سعر).
- الدفعات المرتبطة.
- شريط إجراءات: تحصيل (Primary)، PDF، واتساب، المزيد (حذف/إلغاء).
- **معيار القبول:** لا حساب إجمالي في العميل؛ PDF مطابق للوحة؛ أزرار الحذف للمدير فقط.

### 3.6.15 F3–F6 — إصدار فاتورة

**Wizard من 3 خطوات:**

1. **النوع والجهة:** عداد / اشتراك / وايت → اختيار المشترك → (للعداد) اختيار العداد.
2. **المحتوى:** للعداد: القراءات غير المفوترة (تُعرض تلقائياً مع الوحدات والمبلغ)، سعر الوحدة، خيار إضافة رسوم اشتراك (مع المجموع المستحق)، خيار إضافة وايت (مع المجموع)، ملاحظات. **معاينة حية** للإجمالي والمتبقي المتوقع.
3. **المراجعة والتأكيد:** ملخص + تحذير إن كانت هناك فاتورة غير مسددة سابقة (ستصبح متأخرة) + زر «إصدار».

- **الأخطاء المتوقعة:** «لا توجد قراءات جديدة…» (BR-07) → بطاقة توضيحية مع أزرار بديلة (إصدار فاتورة اشتراك/وايت).
- **الصلاحية:** مدير/محصّل (حسب config).
- **معيار القبول:** لا يمكن إصدار فاتورة فارغة؛ المبالغ المعروضة = مبالغ API بعد الإصدار.

### 3.6.16 G1–G4 — التحصيل (الشاشة الثانية أهمية)

**G1 Collect:**
1. اختيار الحساب: المشترك (حساب عام) أو العداد (حساب معزول) — تبويب واضح.
2. عرض: إجمالي المستحق، عدد الفواتير، متبقي كل فاتورة.
3. اختيار الفاتورة (اختياري؛ افتراضي FIFO).
4. المبلغ: افتراضي = المتبقي (قابل للتعديل)، أزرار سريعة (+1000، +5000، «كامل»).
5. طريقة الدفع: نقداً / حوالة / شيك (المرجع إلزامي للحوالة/الشيك).
6. «وذلك مقابل» (reason) + ملاحظات.
7. ملخص التأثير: «سيُسدَّد 12,500 من فاتورة INV… ويتبقى 0».
8. تأكيد بسحب (Slide to confirm) لتقليل الخطأ.

**G4 النجاح:** رقم السند، المبلغ، المشترك، المتبقي، الرصيد الدائن؛ أزرار: مشاركة واتساب، عرض PDF، تحصيل آخر.

**Offline:** يُسجَّل بسند «معلّق» (رقم مؤقت `LOCAL-...`)، ويُزامن. عند عودة الاتصال يُستبدل برقم السيرفر. **لا** يُطبع/يُشارك السند النهائي قبل المزامنة (يُعرض «سند مؤقت»).

- **معيار القبول:** تحصيل ≤ 25 ثانية؛ منع مبلغ ≤ 0؛ منع مبلغ يتجاوز المستحق + 100,000 دون تأكيد إضافي؛ لا تكرار عند إعادة الإرسال (Idempotency).

### 3.6.17 G5–G6 — السندات

قائمة بفلاتر (تاريخ، محصّل، طريقة)، تفاصيل تعرض كل بيانات السند + الفاتورة المرتبطة + المتبقي، وأزرار PDF/واتساب.

### 3.6.18 H1–H6 — رسوم الاشتراك والوايت

- H1: قائمة، فلاتر بالحالة، إجمالي المستحق، إجراء «فوترة المحدد».
- H2: نموذج بسيط (المشترك، العداد اختياري، المبلغ، ملاحظات، الحالة).
- H4: قائمة طلبات الوايت (تاريخ، مبلغ، حالة، فاتورة)، إجراء «إنجاز» ثم «فوترة».
- **قاعدة:** لا فوترة مزدوجة (الحالة invoiced/paid تُعطّل الزر).
- **معيار القبول:** أخطاء «مفوترة مسبقاً» تظهر كرسالة واضحة لا كخطأ شبكة.

### 3.6.19 I1–I5 — المربعات والتعرفة

- المربعات: اسم، وصف، عدد المشتركين، إجمالي المتأخرات؛ CRUD مع تحذير قبل الحذف (cascade).
- التعرفة: قائمة أسعار (الاسم، سعر الوحدة، الفترة، مفعّل)؛ تفعيل واحد فقط في التاريخ؛ معاينة «السعر الحالي 600».
- **الصلاحية:** مدير فقط.

### 3.6.20 J1–J5 — الإدارة

- J1 المستخدمون: قائمة (الاسم، البريد، الدور، الحالة)، بحث؛ إضافة (اسم/بريد/كلمة مرور/دور)؛ تعديل؛ تعطيل (بدل الحذف P1).
- J2/J3: عرض الأدوار والصلاحيات (قراءة فقط إن لم يكن مديراً أعلى).
- J4 دفتر الأستاذ: قائمة حركات (تاريخ، مشترك، نوع، مبلغ، وصف، مرجع)، فلاتر؛ مجموع.
- J5 تسوية: نوع (دائن/مدين)، مبلغ، سبب إلزامي، مرجع — تتطلب صلاحية `Create:Transaction` وتُسجَّل في audit.

### 3.6.21 K1–K8 — الإعدادات

**K1 فهرس:** بطاقات (عام/الهوية، القراءة، الفاتورة، السند، الرسائل، متقدم، المظهر).
**K2 عام:** اسم المشروع (عربي/إنجليزي)، العنوان، الهاتف 1/2، اسم المحصل الافتراضي، الشعار، الفافيكون، العلامة المائية (رفع/معاينة/حذف).
**K3 القراءة:** الإصدار التلقائي (Switch)، الدورة (Select)، يوم القراءة (Select: آخر يوم/1..28)، مدة السماح (رقم)، اعتبار السابق متأخراً فوراً.
**K4 الفاتورة:** 4 عناوين + جدول حقول (Switch + Label) — 20 صفاً، مع معاينة PDF حية.
**K5 السند:** عنوان + جدول حقول + المبلغ كتابةً + اللاحقة.
**K6 الرسائل:** تفعيل، الطريقة، التوكن (مخفي)، phone_number_id، 4 قوالب (محرر نصوص مع إدراج Placeholders)، معاينة، «إرسال تجريبي».
**K7 متقدم:** كل مفاتيح `settings` (جدول بحث + تعديل)، تحذير «للمدير فقط».
**K8 معاينة القالب:** تعبئة ببيانات نموذجية وإظهار النص النهائي + معاينة PDF.

- **معيار القبول:** حفظ ذري (إما الكل أو لا)؛ التحقق من الأنواع؛ إبطال الكاش؛ لا يظهر التوكن كاملاً.

### 3.6.22 L1–L7 — التقارير

| التقرير | المدخلات | المخرجات | التصدير |
|---|---|---|---|
| L2 التحصيل | من/إلى، مربع، محصّل، طريقة | إجمالي، عدد السندات، متوسط، تفصيل يومي، رسم | Excel |

- **M1 مركز المزامنة:** حالة الاتصال، آخر مزامنة، قائمة العمليات المعلّقة (نوع/تاريخ/حالة/سبب الفشل)، إعادة محاولة/حذف، مزامنة الآن.

- **M8 حول:** الإصدار، رقم البناء، سياسة الخصوصية، الشروط.

### 4.2.1 قواعد الطبقات

| الطبقة | مسموح | ممنوع |
|---|---|---|
| **presentation** | Widgets، Riverpod providers، استدعاء application | لا Dio، لا SQL، لا منطق مالي |
| **application** | تنسيق حالات، تحويل domain ↔ UI، تفاؤلية | لا معرفة بـ BuildContext |
| **domain** | Entities، Repository interfaces، قواعد عمل نقية (حساب الاستهلاك، التحقق) | لا يعتمد على أي حزمة خارجية |
| **data** | DTOs، API، Drift، repositories implementations | لا منطق عرض |

**قاعدة الاعتماد:** `presentation → application → domain ← data`. الاتجاه واحد، والـ DI عبر Riverpod.

```dart
final class ReadingRepositoryImpl implements ReadingRepository {
  ReadingRepositoryImpl(this._api, this._dao, this._queue);
  final ReadingApi _api;          // Retrofit
  final ReadingDao _dao;          // Drift
  final SyncQueue _queue;

  @override
  Future<Result<ReadingEntity>> create(CreateReadingInput input) async {
    final clientUuid = input.clientUuid ?? Uuid().v4();
    final local = await _dao.insertPending(input.copyWith(clientUuid: clientUuid));
    if (await _connectivity.isOffline) {
      await _queue.enqueue(SyncOp.readingCreate(clientUuid, input));
      return Result.ok(local.toEntity());
    }
    try {
      final dto = await _api.create(input.toJson(idempotencyKey: clientUuid));
      await _dao.upsert(dto.toTable());
      return Result.ok(dto.toEntity());
    } on ApiException catch (e) {
      await _queue.enqueue(SyncOp.readingCreate(clientUuid, input));
      return Result.ok(local.toEntity());     // تفاؤلي
    }
  }
}
```

## 4.4 الشبكة والأخطاء

### 4.4.1 `ApiClient` (Dio)

**Interceptors بالترتيب:**
1. **AuthInterceptor**: يضيف `Authorization: Bearer`، ويضيف `Accept-Language: ar`، `X-App-Version`, `X-Device-Id`, `X-Platform`.
2. **IdempotencyInterceptor**: يضيف `Idempotency-Key` لكل `POST` مالي (UUID من العميل).
3. **RetryInterceptor**: 3 محاولات للـ GET، محاولة واحدة للـ POST، backoff 500ms/1s/2s، فقط على 5xx/Timeout.
4. **ErrorMapper**: يحوّل أي خطأ إلى `ApiFailure`.
5. **LogInterceptor**: في debug فقط، مع إخفاء `Authorization` و`password`.

**الإعدادات:** `connectTimeout 20s`, `receiveTimeout 30s`, `sendTimeout 60s` (رفع الصور)، `validateStatus` للتعامل مع 4xx يدوياً.

### 4.4.2 نموذج الخطأ الموحّد (Server)

### 4.5.1 الجداول المحلية (Drift)

| الجدول | المحتوى | سياسة الاحتفاظ |
|---|---|---|
| `cached_subscribers` | المشتركون + الأرصدة | تحديث تفاضلي، حذف غير النشط بعد 90 يوم |
| `cached_meters` | العدادات + آخر قراءة + الفترة | تحديث تفاضلي |
| `cached_invoices` | فواتير آخر 12 شهراً + الحالات | إخلاء الأقدم |
| `cached_payments` | سندات آخر 6 أشهر | |
| `cached_squares` / `cached_tariffs` / `cached_settings` | مراجع | تحديث عند التغيير |
| `pending_ops` | طابور العمليات (create_reading, create_payment, update_subscriber…) | حتى المزامنة |
| `pending_photos` | مسارات الصور غير المرفوعة | حتى الرفع |

**حجم متوقع:** 5,000 مشترك + 8,000 عداد + 20,000 فاتورة ≈ 6–12MB. حد أقصى 50MB مع تنبيه.

### 4.5.2 المزامنة التفاضلية

1. عند البدء/عودة الشبكة/كل 15 دقيقة (foreground) → `GET /sync?since=<cursor>&entities=...`.
2. الاستجابة تحوي `data` و`deleted` (tombstones) و`next_cursor` و`server_time`.
3. تُطبَّق في معاملة واحدة (Drift transaction) — إما الكل أو لا.
4. تُحدَّث `sync_meta`.
5. تُرسل العمليات المعلّقة بالترتيب (FIFO) عبر `POST /sync/batch` أو فردياً.

**معرّف المزامنة (cursor):** `updated_at` + `id` مركّب (لتجنّب فقدان السجلات عند نفس الثانية). السيرفر يعيد `next_cursor` مشفّراً.

### 4.5.3 طابور العمليات (Outbox Pattern)

```dart
class PendingOp {
  final String id;            // uuid
  final SyncOpType type;      // readingCreate, paymentCreate, subscriberUpdate...
  final String payload;       // JSON
  final String? localRefId;   // لربط القراءة بالفاتورة المحلية
  final int attempts;
  final DateTime createdAt;
  final SyncOpStatus status;  // queued, sending, failed, conflict, done
  final String? lastError;
}
```

**قواعد:**
- ترتيب صارم (FIFO) لضمان أن القراءة تُزامن قبل فاتورتها.
- كل عملية لها `client_uuid` تُرسل كـ `Idempotency-Key` → السيرفر يرد بنفس النتيجة عند التكرار.
- فشل 4xx (ما عدا 408/429) = فشل نهائي → `conflict` ويظهر للمستخدم مع الحل.
- فشل الشبكة/5xx = إعادة بلا حد أقصى (مع backoff متزايد حتى ساعة).
- حد أقصى 500 عملية معلّقة → تنبيه «زامن الآن».

### 4.5.4 حل التعارضات (Conflict Resolution)

| الحالة | السياسة |
|---|---|
| قراءة لنفس الفترة أُنشئت على السيرفر | **السيرفر يفوز**؛ تُعلَّم العملية `conflict` وتُعرض للمستخدم للمراجعة (دمج/حذف) |
| قراءة أقل من السابقة (تغيّرت على السيرفر) | تُرفض، مع إظهار القراءة السابقة الجديدة |
| دفعة على فاتورة سُدّدت/حُذفت | تُرفض، ويُعرض «تغيّرت الفاتورة» مع خيار إعادة التوجيه لرصيد دائن (بموافقة) |
| تعديل مشترك (تعارض حقول) | Last-Write-Wins مع تسجيل في audit، إلا الحقول المالية (لا تُعدَّل من العميل) |
| تعديل إعدادات | السيرفر يفوز دائماً |

**قاعدة ذهبية:** العمليات المالية لا تُدمج تلقائياً أبداً؛ تُعلَّق لمراجعة بشرية.

### 4.5.5 مؤشرات المزامنة في الواجهة

- شريط أعلى: `متصل • آخر مزامنة 10:42` أو `غير متصل • 3 عمليات معلّقة`.
- في القوائم: عناصر معلّقة تحمل شارة «في الانتظار».
- في مركز المزامنة: تفاصيل + إعادة محاولة + حذف (بحذر) + «مزامنة الآن».

> هذا القسم هو **المواصفة الملزمة** بين فريق الـ Backend وفريق Flutter. أي نقطة نهاية تُضاف أو تُعدَّل يجب أن تُحدَّث في `docs/api/openapi.yaml` أولاً (Contract-first) ويُولَّد منها كود Flutter (Retrofit) وأمثلة الاختبار.

## 5.1 المبادئ العامة

| # | المبدأ |
|---|---|
| API-01 | كل المسارات تحت `/api/v1`. |
| API-02 | REST + أسماء جمع، أفعال عبر HTTP methods. |
| API-03 | JSON فقط، `Content-Type: application/json`، الترميز UTF-8. |
| API-04 | كل المبالغ `string` بصيغة `"12345.67"` (لتفادي أخطاء الفاصلة العائمة). |
| API-05 | كل التواريخ `YYYY-MM-DD`، والتواريخ الزمنية ISO-8601 مع المنطقة `+03:00` (Asia/Aden). |
| API-06 | الترقيم: `?page=1&per_page=25` (max 100)، والاستجابة تحوي `meta`. |
| API-07 | الفرز: `?sort=-bill_date,id`. |
| API-08 | التضمين: `?include=subscriber,meter` (قائمة بيضاء لكل نقطة). |
| API-09 | البحث: `?q=` + فلاتر صريحة. |
| API-10 | كل استجابة تحمل `X-Request-Id` و`X-Server-Time`. |
| API-11 | لا تُرجع الحقول الحساسة (password, tokens, deleted_at إلا للمدير). |
| API-12 | الأخطاء بصيغة موحّدة (5.3). |
| API-13 | كل عملية كتابة مالية تقبل `Idempotency-Key` وتُرجع نفس الاستجابة عند التكرار. |
| API-14 | الصلاحيات على كل مسار (`permission:`). |
| API-15 | لا حذف نهائي من التطبيق؛ كل الحذف Soft Delete + استعادة للمدير. |

## 5.2 المصادقة والصلاحيات

### 5.2.1 تسجيل الدخول

`POST /api/v1/auth/login`

```json
// Request
{ "email": "admin@example.com", "password": "secret", "device_name": "Samsung A15", "device_id": "a1b2c3", "platform": "android", "app_version": "1.0.0+100" }
```

```json
// 200 Response
{
  "data": {
    "token": "1|9xQ...",
    "token_type": "Bearer",
    "expires_at": "2027-01-21T10:00:00+03:00",
    "user": {
      "id": 12, "name": "مدير النظام", "email": "admin@example.com",
      "avatar_url": "https://.../storage/avatars/x.jpg",
      "roles": ["super_admin"],
      "permissions": ["ViewAny:Invoice", "Create:Payment", "..."],
      "is_super_admin": true
    }
  }
}
```

- **Rate limit:** 5 محاولات/دقيقة/IP ثم 429 مع `Retry-After`.
- **أخطاء:** 422 `VALIDATION_FAILED`؛ 429 `RATE_LIMITED`؛ 403 `ACCOUNT_DISABLED` (إن أُضيف حقل الحالة).

| المورد | super_admin/admin | collector | meter_reader |
|---|---|---|---|
| المشتركون | CRUD | R | R |
| العدادات | CRUD | R | R |
| القراءات | CRUD + حذف | R | C + R |
| الفواتير | CRUD + إصدار + حذف | R + إصدار | R |

## 5.3 الغلاف والترقيم والأخطاء

### 5.3.1 غلاف النجاح

```json
// عنصر واحد
{ "data": { "id": 1 } }

// قائمة مع ترقيم
{
  "data": [ ... ],
  "meta": {
    "current_page": 1, "per_page": 25, "total": 312, "last_page": 13,
    "from": 1, "to": 25
  },
  "links": { "next": "...?page=2", "prev": null }
}
```

> **استثناء مؤقت:** نقاط النهاية القديمة (بدون v1) تُبقي الشكل القديم للتوافق. أما v1 فكلها بالغلاف.

### 5.3.2 غلاف الخطأ

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "البيانات المدخلة غير صحيحة.",
    "fields": { "current_reading": ["القراءة الحالية يجب أن تكون أكبر من أو تساوي القراءة السابقة (1240)"] },
    "trace_id": "01JABCD2XYZ"
  }
}
```

**جدول أكواد الأخطاء:**

| Code | HTTP | المعنى |
|---|---|---|
| `VALIDATION_FAILED` | 422 | حقول غير صحيحة |
| `UNAUTHENTICATED` | 401 | توكن مفقود/منتهٍ |
| `INVALID_CREDENTIALS` | 422 | بيانات دخول خاطئة |
| `FORBIDDEN` | 403 | لا صلاحية |
| `NOT_FOUND` | 404 | غير موجود |
| `ALREADY_INVOICED` | 409 | مفوتر مسبقاً |
| `READING_LOCKED` | 423 | قراءة مفوترة لا تُعدّل/تُحذف |
| `PERIOD_DUPLICATE` | 409 | فترة مكررة |
| `READING_LESS_THAN_PREVIOUS` | 422 | قراءة أقل من السابقة |
| `NO_BILLABLE_ITEMS` | 409 | لا يوجد ما يُفوتر |
| `INSUFFICIENT_DATA` | 422 | بيانات ناقصة لحساب الفترة |
| `IDEMPOTENCY_MISMATCH` | 409 | نفس المفتاح بجسم مختلف |
| `CONFLICT` | 409 | تعارض نسخة |
| `RATE_LIMITED` | 429 | تجاوز الحد |
| `SERVER_ERROR` | 500 | خطأ غير متوقع |
| `SERVICE_UNAVAILABLE` | 503 | صيانة |

## 5.6 التزامن وعدم التكرار (Idempotency)

### 5.6.1 جدول `idempotency_keys`

| الحقل | النوع |
|---|---|
| id | bigint |
| key | string(64) unique |
| user_id | FK |
| endpoint | string |
| request_hash | string(64) |
| response_code | int |
| response_body | json |
| created_at / expires_at | timestamps |

- مدة الاحتفاظ: 7 أيام.
- عند تكرار المفتاح بنفس الجسم: تُعاد الاستجابة المخزنة (200/201 نفسها).
- عند نفس المفتاح بجسم مختلف: 409 `IDEMPOTENCY_MISMATCH`.
- Middleware: `Idempotency` يُطبَّق على كل POST مالي.

### 5.6.2 قفل توليد الأرقام (حل G-04)

```php
// app/Services/SequenceService.php
public function next(string $key, string $prefix, int $pad = 4): string
{
    return DB::transaction(function () use ($key, $prefix, $pad) {
        $row = DB::table('sequences')->where('key', $key)->lockForUpdate()->first();
        if (! $row) {
            DB::table('sequences')->insert(['key' => $key, 'value' => 0]);
            $row = DB::table('sequences')->where('key', $key)->lockForUpdate()->first();
        }
        $next = $row->value + 1;
        DB::table('sequences')->where('key', $key)->update(['value' => $next]);
        return $prefix . str_pad((string) $next, $pad, '0', STR_PAD_LEFT);
    });
}
```

## 5.7 الملفات والصور وPDF

### 5.7.1 رفع الصور

1. `POST /uploads` (multipart، `file`, `type=reading`) → `{id, url, thumb_url, size, mime}`.
2. الحد: 5MB قبل الضغط، والعميل يضغط إلى ≤ 300KB و`max 1600px`.
3. التحقق من MIME الفعلي (magic bytes) لا الامتداد.
4. تخزين: `storage/app/public/readings/{yyyy}/{mm}/` أو S3.
5. العرض: رابط موقّع 60 دقيقة (لا مسار عام).

### 5.7.2 PDF

- `GET /invoices/{id}/pdf` → `application/pdf` مع `Content-Disposition: inline; filename="INV-...pdf"`.
- يُولَّد عبر `spatie/laravel-pdf` + Browsershot كما في `routes/web.php`.
- **تحسين مطلوب:** التخزين المؤقت (cache) للـ PDF لمدة 24 ساعة أو حتى تعديل الفاتورة، مع `ETag`.
- **خطة بديلة:** إن تعذّر Chromium، الخطأ 503 مع رسالة «PDF غير متاح مؤقتاً — يمكن مشاركة ملخص نصي» + تسجيل في Sentry.
- الحجم المتوقع: 80–200KB (A5 أفقي).
- التطبيق: تنزيل → تخزين مؤقت → `printing` للعرض → `share_plus` للمشاركة.

### 5.7.3 روابط المشاركة

`GET /invoices/{id}/share-link` → `{url, expires_at}` (Signed URL صالح 30 دقيقة) يُستخدم في واتساب.

### 7.4.5 قوالب أوامر جاهزة (Copy/Paste)

**1) وكيل فهم الكود (يُستخدم أولاً دائماً):**

```
اقرأ docs/MOBILE_APP_MASTER_PLAN_AR.md (الأقسام 2.2، 2.3، والقسم المتعلق بمهمتي)
ثم استكشف الكود المتعلق بـ <الموضوع>.
أخرج:
1) الملفات المسؤولة (مسارات + أسطر).
2) تدفق التنفيذ خطوة بخطوة.
3) قواعد العمل المؤثرة (BR-..).
4) المخاطر/الأخطاء الحالية.
5) ما يجب أن أقرأه قبل التنفيذ.
لا تعدّل أي ملف في هذه المهمة.
```

**2) وكيل بناء نقطة API:**

```
المهمة: تنفيذ <METHOD> <PATH> وفق القسم 5.
القيود:
- لا تعدّل PaymentService/InvoiceService.
- استخدم FormRequest + API Resource + Policy.
- أضف Idempotency إن كانت العملية مالية.
- أضف اختبارات Feature (نجاح، تحقق، صلاحية، تكرار).
- حدّث openapi.yaml وأضف مثالاً في docs/api/examples.
أخرج PR صغيراً + ملخص + مخرجات الاختبارات.
```

**3) وكيل بناء شاشة Flutter:**

```
المواصفة: القسم 3.6.8 (إدخال قراءة).
استخدم فقط مكونات core/widgets و theme.
أضف الحالات: loading, empty, error, offline.
أضف مفاتيح (Keys) للاختبار.
اكتب Widget Test لكل حالة + Golden test للشاشة الأساسية.
لا تحسب أي مبلغ في الواجهة؛ اعتمد على API.
أخرج الكود + الاختبارات + لقطات golden.
```

**4) وكيل المراجعة الناقد:**

```
أنت مراجع صارم. راجع هذا الـ diff مقابل:
- القسم 2.3 (قواعد العمل) و3.4 (التصميم) و4 (المعمارية) و5 (العقد).
أخرج:
1) أخطاء حرجة (Blockers) مع الملف والسطر.
2) مخالفات للعقد.
3) مشاكل أداء/ذاكرة.
4) نقص اختبارات.
5) تحسينات اختيارية.
لا تجامل. إن لم تجد مشكلة قل ذلك صراحة.
```

**5) وكيل اختبار E2E:**

```
اكتب سيناريو Patrol لـ: <وصف>.
الشروط: يبدأ من حالة تطبيق نظيفة، يستخدم بيانات الاختبار من fixtures،
يتحقق من النصوص العربية، ويعمل على Android API 34.
أضف تعليقات بالخطوات، والتقط لقطة عند الفشل.
```

**6) وكيل تحليل العيب:**

```
هذا تقرير عيب: <...> وهذه اللوجات: <...>.
أخرج: السبب الجذري المحتمل (مرتب بالملف/السطر)، وخطوات إعادة إنتاج مختصرة،
وإصلاحاً مقترحاً، واختبار انحدار يمنع التكرار.
```

### 7.4.6 ممنوعات على الوكلاء (Anti-patterns)

| ممنوع | السبب |
|---|---|
| «أصلح كل المشروع» | تغييرات ضخمة غير قابلة للمراجعة |
| تعديل هجرة قديمة | يكسر بيئات أخرى |
| إضافة مكتبة جديدة بلا موافقة | تضخم/مخاطر أمنية |
| توليد بيانات مالية وهمية في بيئة staging مشتركة بلا وسم | يفسد الاختبار |
| حساب مبالغ في الواجهة | يخالف ADR-06 |
| تجاهل RTL | يكسر تجربة المستخدم الأساسية |
| حذف اختبار فاشل | يخفي عيباً |
| استعمال `!` (force unwrap) في Dart بلا سبب | انهيارات |
| `print` في الكود | يسرّب بيانات |

### 7.4.7 كيف يقيس الفريق أثر الوكلاء؟

| المقياس | الهدف |
|---|---|
| وقت تنفيذ مهمة متوسطة | انخفاض 30–40% |
| نسبة PRs المرفوضة | < 15% |
| تغطية الاختبارات | +10 نقاط |
| عيوب ما بعد الدمج | انخفاض 25% |
| رضا الفريق (استبيان) | ≥ 7/10 |

**تنبيه:** إذا ارتفعت نسبة PRs المرفوضة عن 25%، تُراجع قوالب الأوامر وتُضاف قيود.

## 7.5 سير العمل التعاوني

### 7.5.1 دورة حياة المهمة

```
Backlog → Ready (DoR) → In Progress → In Review → QA → Done (DoD)
             ↑                              ↓
             └────────── إعادة عمل ─────────┘
```

### 7.5.2 Definition of Ready (DoR)

- [ ] المهمة مرتبطة ببند في هذه الوثيقة (رقم شاشة/نقطة API/BR).
- [ ] معايير القبول مكتوبة وقابلة للقياس.
- [ ] التصميم جاهز (إن كانت واجهة).
- [ ] العقد (OpenAPI) محدّث.
- [ ] الاعتماديات مكتملة أو محلولة.
- [ ] التقدير ≤ 3 أيام (وإلا تُقسَّم).

### 7.5.3 Definition of Done (DoD)

- [ ] الكود مدموج في `main` عبر PR مُراجع.
- [ ] اختبارات (وحدة/Widget) موجودة وناجحة.
- [ ] `flutter analyze` / `pint` بلا أخطاء.
- [ ] لا انخفاض في التغطية.
- [ ] مُختبر يدوياً على جهاز حقيقي.
- [ ] يعمل offline (إن كان مطلوباً) ومُختبر.
- [ ] RTL + dark + textScale 2.0 سليمة.
- [ ] الوثائق/OpenAPI محدّثة.
- [ ] لا TODO بلا تذكرة.
- [ ] QA وافق.

### 7.5.4 قواعد الـ PR

- عنوان: `feat(readings): offline queue for meter readings`
- وصف: ماذا/لماذا/كيف/كيف اختُبر/لقطات/قياسات.
- حجم: ≤ 400 سطر (استثناء: توليد كود).
- مراجع واحد على الأقل، واثنان للمال/الأمان/الهجرات.
- لا دمج إن كان CI أحمر.
- Squash merge، مع حذف الفرع.

### 7.5.5 نموذج الـ PR (يُوضع في `.github/pull_request_template.md`)

```markdown
## ماذا
<!-- وصف مختصر -->

## لماذا
<!-- البند المرجعي: الشاشة 3.6.8 / النقطة 5.4.5 / BR-13 -->

## كيف
<!-- القرارات التقنية -->

## الاختبار
- [ ] unit
- [ ] widget
- [ ] integration/E2E
- [ ] يدوي على: <device>
- [ ] offline
- [ ] RTL/Dark/TextScale

## لقطات
## ملاحظات للمراجع
```

- **نسبة إعادة العمل المتوقعة:** 10–15% (تُغطّى بالهامش).

# 11. ما بعد الإصدار الأول

## 11.1 الإصدار 1.1 (شهر 4)

- إلغاء الفواتير (Void) بدل الحذف.
- التقارير المتقدمة + لوحات مخصصة.
- الجدولة: تعيين مربعات للقراء ومهام يومية.
- وضع «المشرف» الكامل.
- دعم إنجليزي كامل.
- تحسينات الأداء (isolate PDF، تقليل الحجم).

- **بوابة المشترك:** تسجيل بالهاتف + OTP، فواتيري، رصيدي، سنداتي، طلب وايت، شكوى.

- إشعارات للمشتركين عبر واتساب/SMS.

## 11.3 الإصدار 2.0 (شهر 7+)

- **تعدد المشاريع (Multi-tenant):** عدة مشاريع مياه في تطبيق واحد، عزل بيانات كامل.
- القارئ الذكي: OCR لصورة العداد (كاميرا تقرأ الرقم).
- تحليلات تنبؤية: توقع الاستهلاك، كشف التسرب (استهلاك شاذ).
- خرائط: مواقع العدادات، مسارات القراءة المثلى.
- وضع بلا إنترنت كامل للتقارير.
- تكامل محاسبي (تصدير قيود إلى نظام محاسبة).

```dart
class SyncEngine {
  SyncEngine(this._api, this._db, this._queue);

  Future<SyncReport> sync() async {
    final report = SyncReport();
    if (_queue.hasPending) {
      final results = await _queue.flush(_api);
      report.pushed = results.where((r) => r.ok).length;
      report.conflicts = results.where((r) => r.isConflict).toList();
    }
    final since = await _db.meta.cursor();
    final page = await _api.pull(since: since);
    await _db.transaction(() async {
      for (final entity in page.entities) { await entity.applyTo(_db); }
      await _db.meta.setCursor(page.cursor);
    });
    report.pulled = page.count;
    return report;
  }
}
```
